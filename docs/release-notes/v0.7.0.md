# JSPARK Forge v0.7.0

*Better checks for long builds: fail early, read results without logs, repeat only what failed.*

Released 2026-11-22.

**Install** (superpowers comes with it; no setup step):

```
/plugin install jspark-forge --marketplace harishgoswami23/jspark-forge
```

Already installed: it updates by itself when Claude Code starts. Needs Node.js 18 or newer.

## Where this came from

In a real project, a build graph's long end-to-end test run was where the hours went. It died late for reasons that
could have been checked first, its results had to be read out of long logs, one failing test meant running everything
again, and a test that failed once and passed the next time looked the same as a broken one. This release is about
that one step: the check ("gate") of a build graph.

## New: a check step can say more

```
## e2e (gate)
- before: free memory 4 GB
- before: port 5432 open
- before: port 3000 free
- before: container app-db running
- run: npx playwright test
- retry: npx playwright test --last-failed
```

- **`before:` — do not fail 20 minutes in.** What must be true before the check starts: free memory, a port that
  must be open (a database) or free (the port your test server takes), a Docker container that must be running. If
  something is missing, the check is **not started** and nothing fails. You are told what is missing in plain words
  ("free memory is 2.1 GB, needs 4 GB"). These are fixed forms; nothing from the file is run as a command.
- **`retry:` — repeat only what failed.** Your test tool's own command for "run only what failed last time". When the
  full run fails, the check is not failed yet: only what failed runs again. If that passes, the full command must
  pass **once more**. A retry alone never completes a check. If the retry fails, the check fails.
  It is a command, so `TRUST GRAPH` shows it to you first, like the `run:` line.

## New: results without reading logs

- Every run of a check's command is recorded: how many tests passed, failed, were skipped or did not run, and the
  names of the failing ones. JSPARK Forge reads this from the output of node:test, TAP, jest, vitest, pytest,
  Playwright, mocha and go test. For any other tool the exit code is kept and the counts are left out.
- `graph gate` now keeps each run's whole output in a file (`.jspark-forge/state/gatelog-<graph>-<step>-<n>.log`, the
  last 5 per step) and tells Claude the summary. On a failure it also prints the last lines. Before, the whole output
  went to Claude, which cost tokens on every long run.
- `graph status` lists a check's runs one under the other, so two runs can be compared at a glance.
- The exit code still decides pass or fail. Counts and names are for people; they never turn a failure into a pass.

## New: flaky is said out loud

- A test that failed and then passed **with no change to the code** is recorded as flaky, and named every time: when
  the check passes, in `graph status`, and when the build finishes. The message says a flaky test is not a fixed
  test.
- If the code changed between the two runs, nothing is called flaky: the test may have been fixed.

## New: how far, and how much

- Ask "how far is it?" while a check runs in the background: `graph status` answers from the run's log, for example
  "31 of 63 tests done, 0 failed".
- Every step now ends with one line: steps done, minutes and tokens so far, and the last step's own figures. An
  expensive step shows while there is still a choice. Tokens are known for helper steps only.

## New: Claude stays reachable while it works

- A message you send while Claude works reaches it only when its current command ends. With a 10-minute test run in
  front, a simple question ("can I start Docker?") waited 10 minutes.
- JSPARK Forge now tells Claude at every session start: run anything longer than about a minute in the background,
  and answer the user's mid-task message first. `- stay-reachable: off` under `## Settings` switches it off.
- It is a rule, not a hook: nothing can interrupt a command that is already running. For that case Claude Code has
  `/btw <question>` (a quick answer at once; it sees the conversation, not the code) and Ctrl+Enter (a waiting message
  lands now; the running command moves to the background). The README says so.

## Nothing changes for a graph without the new lines

A check with only `run:` lines behaves as before, and a graph you trusted before is not asked about again.

## Limits, said plainly

- "No change to the code" means no change **git can see**: the commit, changes to tracked files, and new files git
  does not ignore (by size and time written). A change inside a file that git ignores is not seen. If your tests
  leave new files that git does not ignore, the code looks changed and nothing is called flaky (the safe direction).
- A command that ended without an exit code (the tool call timed out) is never counted as a test failure for the
  flaky list.
- JSPARK Forge cannot check that your `retry:` command really runs only the failed tests. It does not need to: the
  full run at the end is what makes the result safe.
- The `before:` checks are made when the check is handed out and when `graph gate` starts. A command Claude runs by
  hand with the Bash tool afterwards is not checked again.
- The counts for a command run with the Bash tool come from the output the tool reports, which can be cut short.
  The verdict is not affected.
- The new lines have run in tests on three systems, not yet in a real long build. The first real use is the proof.

## Still open

- The demo GIF in the README is an animation of the flow, made by `docs/launch/make_demo_gif.py`, and the README
  says so. A real screen recording would be better (`docs/demo-gif-script.md` says how).
- The code map does no per-file refresh of its own and uses no git post-commit hook; read-only sources record no
  "last read". All three are written in the spec as deviations.
