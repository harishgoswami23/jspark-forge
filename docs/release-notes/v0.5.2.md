# JSPARK Forge v0.5.2

*A build graph's check can now take longer than 10 minutes.*

Released 2026-11-21.

**Install** (superpowers comes with it; no setup step):

```
/plugin install jspark-forge --marketplace harishgoswami23/jspark-forge
```

Already installed: it updates by itself when Claude Code starts. Needs Node.js 18 or newer.

## Fixed

- **A check that outlasts one tool call.** A build graph's check (a `gate` step) was recorded only when its command
  finished inside one tool call. One tool call waits 10 minutes at most; a longer command is moved to the background,
  and its result never reached JSPARK Forge. So a graph with a 19-minute end-to-end suite stayed at "running" whatever
  the tests said.
  Now Claude runs `forge.js graph gate <name> <step>` in the background for such a check. JSPARK Forge runs the
  check's own commands itself (the ones you trusted with `TRUST GRAPH`), one after another, in the project folder,
  with no time limit, and records each real exit code. A failing command stops the run and is named, as before.
- **A check left at "running" says what to do.** `graph next` now names the commands a check still needs and the
  command that runs them, so a check whose command went to the background, or whose session was cut off, is not a
  dead end.

## Limits

- The check runner only runs in the session that runs the graph, and only commands that are still pending. Its call
  must be the whole command, exactly as `graph next` prints it: a variable or `cd` in front, anything after it, or a
  helper running it is blocked. This is pattern matching, like the rest of the block list.
- It never runs a command the block list would hold or ask about; that command goes through Claude's tool, where you
  are asked. Claude Code's own allow, ask and deny rules for single commands do not see the check's commands when the
  runner runs them: your `TRUST GRAPH` is the approval.
- A result is recorded only into the same run and the same hand-out of the step: stop or restart the graph while a
  command runs and its result is dropped.
- If the runner is killed (the session ends, the machine goes down), nothing is recorded for the command it was
  running: the check stays at "running" and the same command runs it again from that command on. The test command
  itself may keep running; on Windows a killed test command reads as a failure.
- The shell is fixed: `/bin/bash` (or `/bin/sh`) on macOS and Linux, Git Bash on Windows. Without Git Bash on Windows
  the runner refuses and the commands go through Claude's tool.
