# JSPARK Forge: plain instructions

For tools that cannot install the JSPARK Forge plugin. Generated by `scripts/build-plain.js` from the same files
the plugin uses; do not edit it by hand.

## Grounding rule

JSPARK Forge grounding rule:
1. When you say where something is in the code, cite path:line, from the map or from a file you read.
2. If you cannot find it, say "not found". Never guess a path, name or line.
3. Never describe code you have not read in this session. Read it first, or say you have not.
4. Handoffs, summaries and memory are pointers, not proof. Re-read the file before relying on them.
5. Specs, architecture and schema live in the repo. Read them there, not from memory.

## Commands to stop and ask about

Before you run any of these, stop and ask the user to confirm in words. Never run them on your own.

- rm-rf-outside: this deletes a folder outside the project, or the project itself or its history. Worse: this would delete your home folder, the whole disk or a whole drive
- git-force-push-main: this force-pushes to main or master and can erase commits on the shared branch
- git-reset-hard: this throws away your uncommitted work
- git-clean-fdx: this deletes every untracked and ignored file, including local settings and .env files
- git-stash-drop: this permanently deletes saved stashes
- sql-destroy: this deletes database tables or every row of a table (DROP, TRUNCATE, or DELETE without WHERE)
- db-write: this writes to a production database (an insert, update, schema change, migration, merge, reset or restore; reads are never blocked)
- secret-files: this changes a secrets or key file (.env, keys, credentials)
- chmod-wide: this opens file permissions to everyone or changes a whole folder tree
- pipe-to-shell: this runs a script straight from the internet without showing it first
- guest-quarantine: this runs code from a repo you are reviewing (install, build, test or run), and that code can do anything your user account can
- readonly-source: this changes a read-only source listed in rules.md (an old system being migrated from)

## Skill template

One reusable task. Copy it to `skills/<name>/SKILL.md` and never overwrite an existing file.

````markdown
---
name: summarise-document
description: Use when asked to read a document at a URL or path and write a summary into docs/knowledge/.
---
<!--
JSPARK Forge skill template. Copy to skills/<name>/SKILL.md, then replace the example below. One task per skill.
Write in the imperative, second person. Run `forge.js lint` on the file before you use it.

- name: the folder name of the skill, lower case with hyphens.
- description: one line that states the trigger, and must start with "Use when".
- Numbered parts: each part names its Input, its Action and its Output (a name or a path).
- A fetched or generated artifact: skip its part if the output already exists.
- Output names never overwrite: check that the name is free, and if it is taken, stop and say so.
- Last part: "Verify:" with "Evidence:", the check that ran and the output that proves it.
-->
1. Input: the URL or path. Action: normalise it to a cache key. Output: the key.
2. Input: the key. Action: if `.cache/<key>/` exists, skip; else fetch and unpack there. Output: `.cache/<key>/`.
3. Input: the cache folder. Action: find the entry file; read it and the files it includes. Output: notes (not written).
4. Input: the notes. Action: write `docs/knowledge/summary-<tag>.md`; if it exists, stop and say so. Output: the path.
5. Verify: the file exists, is under 600 words, and quotes one source line with its location.
   Evidence: the word count and the quoted line with its path.
````

## Brief template

One job for one helper. Copy it to `.jspark-forge/briefs/<name>.md` and never overwrite an existing file.

````markdown
<!--
JSPARK Forge brief template. One job for one helper. Copy to .jspark-forge/briefs/<name>.md, then replace the example.
Keep the fields in this order. Run `forge.js lint` on the file before you hand it over.

- Goal: one sentence.
- CAN change: the files the helper may change, as globs.
- CANNOT change: the files it must not touch, as globs.
- Done: one definition of done, or one named metric with a direction ("p95_ms, lower wins").
- Setup: what to read and check first, then wait for "go" before any autonomous work (optional).
- Log: a fixed-schema, append-only table; rows are never reset or rewritten (optional).
- Retries: a number; after that many retries, log and skip (default 2, optional).
- Tie-break: when two versions pass, the simpler one wins (optional).
- Stop: an explicit stop condition (attempts, budget or time) plus a human gate. Never "never stop".
- Outputs: the fields the next step consumes, as a comma list of names (optional).
-->
Goal: make the import step idempotent.
CAN change: src/import/**, tests/import/**
CANNOT change: src/db/schema.*, scripts/measure-import, package manifests
Done: tests/import pass and `scripts/measure-import` reports duplicates = 0
Setup: read docs/plans/import.md; run the test suite once; report the baseline; wait for "go"
Log: .jspark-forge/briefs/import-idempotent.tsv (attempt, commit, duplicates, status keep|discard|crash, note)
Retries: 2, then log and skip
Tie-break: simpler wins
Stop: after 3 kept attempts or 90 minutes; hand back and wait
Outputs: commit, test_totals, leftovers
````

## Model map

Pick the model by the kind of job. Planning and review: strongest. Building from a reviewed plan: standard.
Mechanical checks: light.

- strongest: fable. Why: a mistake here is expensive or invisible until late: specs, designs, plans, architecture and data-model choices, reviews, security, migrations, the release go/no-go
- standard: sonnet. Why: building from a reviewed plan: the plan carries the judgement and the tests catch slips
- light: haiku. Why: mechanical work where a mistake is cheap and visible: running tests, reading logs, renames, moves, version bumps, formatting
